# 前端交互与验收闭环

本参考对齐 RFC-0003，并作为 Agent 解释前端闭环和验收场景的依据。

## 前端闭环

- 前端只展示 FastAPI 返回的结构化状态；
- 会议室列表、日历、预约详情、规则配置和平面图状态都来自同一套 FastAPI 状态；
- 冲突、午餐、临时禁用、组合空间约束都由后端判断；
- 自然语言预约先返回候选，用户确认后再创建；
- 自然语言配置先预览影响摘要，用户确认后再写入系统状态。

## 核心验收场景

- 登录后可以查询会议室列表，默认空间包含活动室、会议室一、会议室二、503、505、506；
- 下周二 10:00-11:00 查询小会议室时，503、506 可用，505 因周二全天不可用被排除；
- 明天中午预约活动室时，因午餐规则被拒绝；
- 创建会议室一+会议室二组合预约后，成员房间不能再被分别预约；
- “504 全天临时维修”后改为“只停用下午”时，只更新同一条规则；
- 取消预约后对应时段释放，并可重新预约；
- 平面图状态必须与日历、规则和预约状态一致；
- Swagger/OpenAPI 必须能展示所有 API、请求和响应模型。

## Agent 回复准则

- 用中文、简洁、结构化回答；
- 明确展示可用、不可用、冲突原因、`state_revision` 和下一步建议；
- 不承诺真实日历、支付、餐厅、外部会议室系统、管理员/RBAC 或强制覆盖冲突；
- 写操作必须说明已确认、已生成幂等键、已携带状态版本，并返回新的 `state_revision`。
